# Software Requirements Specification (SRS)

**Status:** Draft — requires stakeholder sign-off  
**Version:** 0.1

## 1. Purpose
Specify observable requirements for the Dr. Nivedita Ganguli public website, Learning Academy, school portal, parent portal and restricted professional assessment workflow.

## 2. System context
The system has four product modules:
1. Public website and content management.
2. Learning Academy and commerce.
3. School/parent educational assessment workflows.
4. Restricted professional emotional-wellbeing screening.

Shared services: authentication, authorization, consent, audit, notification, file storage, payment reconciliation and reporting.

## 3. Functional requirements

### 3.1 Public website
- FR-PUB-001: Display approved biography, qualifications, services, courses, FAQs and contact information.
- FR-PUB-002: Every public page must be responsive and keyboard accessible.
- FR-PUB-003: Only authorized content editors may publish public content.
- FR-PUB-004: Do not publish unverified credentials, testimonials, clinical claims or student information.
- FR-PUB-005: Contact form must validate inputs, apply rate limits and avoid exposing submitted data in URLs or public logs.

### 3.2 Authentication and account management
- FR-AUTH-001: Users can register, sign in, sign out and recover access through the selected identity provider.
- FR-AUTH-002: Privileged users must use MFA where supported and required by policy.
- FR-AUTH-003: Sessions must be revocable; role changes and account suspension must take effect promptly.
- FR-AUTH-004: Authentication state must be validated with the backend, not trusted solely from browser storage.
- FR-AUTH-005: Account linking and parent-child linking require verification and must resist enumeration.

### 3.3 Multi-tenant schools
- FR-SCH-001: A school administrator can manage only their own organization and permitted campuses.
- FR-SCH-002: Authorized staff can create academic years, classes and teacher assignments.
- FR-SCH-003: Authorized users can import a CSV roster with preview, validation, duplicate detection and a downloadable error report.
- FR-SCH-004: Imports must be transactional or safely resumable; invalid rows must not silently create partial, misleading records.
- FR-SCH-005: Teachers can access only assigned students and classes.
- FR-SCH-006: Deactivated memberships must lose access promptly.
- FR-SCH-007: School exports must be permission-checked, audited and limited to necessary fields.

### 3.4 Parents and child profiles
- FR-PAR-001: A parent can create an account and submit a request to establish a child profile.
- FR-PAR-002: The system must verify guardian authority according to the approved policy before granting access to child records.
- FR-PAR-003: Parents can access only linked children and reports explicitly permitted for parent viewing.
- FR-PAR-004: A child profile created by a parent must not automatically merge with a school record.
- FR-PAR-005: Any authorized cross-context linking or sharing must record purpose, authorization, scope and audit event.

### 3.5 Questionnaires and observations
- FR-AS-001: Authorized school users can draft locally developed questionnaires within configured limits.
- FR-AS-002: Published versions are immutable; edits create a new version.
- FR-AS-003: Each questionnaire records owner, purpose, audience, language, status, approval and whether it is validated or locally developed.
- FR-AS-004: Locally developed questionnaires must not be represented as validated psychometric or clinical instruments.
- FR-AS-005: Teachers can record contextual, observable behaviours for assigned students.
- FR-AS-006: Observation facts and interpretations must be stored/displayed separately.
- FR-AS-007: The system must not infer a mental-health diagnosis from a questionnaire or free-text observation.
- FR-AS-008: Assessment assignments require applicable consent/authorization checks before release.
- FR-AS-009: Results must identify the instrument version and the approved interpretation/scoring version, if any.
- FR-AS-010: Only approved scoring configurations can produce scored results.

### 3.6 Professional wellbeing screening
- FR-CLIN-001: Screening instruments must be registered and approved by an authorized professional before use.
- FR-CLIN-002: Screening sessions and results use a separate permission boundary from educational observations.
- FR-CLIN-003: Only authorized professionals assigned to a case can access restricted screening records.
- FR-CLIN-004: Screening results require the review workflow defined by the professional governance policy.
- FR-CLIN-005: No automatic diagnosis, disease label, or treatment recommendation may be generated by the platform.
- FR-CLIN-006: Any urgent concern workflow must be defined and approved by the professional owner before launch.
- FR-CLIN-007: The system must display scope and limitation statements to authorized viewers.

### 3.7 Courses and payments
- FR-COURSE-001: Authorized content editors can draft, preview, publish, unpublish and version courses.
- FR-COURSE-002: Each course has title, description, audience, price, currency, duration/format, learning outcomes, lesson list and terms.
- FR-COURSE-003: Course assets are private unless intentionally public.
- FR-PAY-001: Order totals are calculated server-side and stored as integer minor currency units.
- FR-PAY-002: Payment status is confirmed through provider verification/webhook reconciliation, not frontend redirect alone.
- FR-PAY-003: Webhook processing is idempotent and rejects invalid signatures.
- FR-PAY-004: Course access is granted only after verified successful payment or authorized manual grant.
- FR-PAY-005: Refunds, cancellations, failed payments and duplicate events have defined state transitions.
- FR-PAY-006: The system does not store raw card data.

### 3.8 Reports, audit and privacy requests
- FR-AUD-001: Sensitive reads, exports, role changes, publication, screening review and consent changes produce audit events.
- FR-AUD-002: Audit logs must not contain passwords, tokens, raw assessment responses or unnecessary sensitive content.
- FR-PRIV-001: Authorized staff can process applicable access, correction, withdrawal and deletion requests.
- FR-PRIV-002: Retention rules are configurable by data category and legal requirements.
- FR-PRIV-003: Deletion workflows must consider dependent records, legal holds, backups and audit retention.
- FR-PRIV-004: A data breach response procedure and responsible contact must be documented.

## 4. Non-functional requirements
- NFR-SEC-001: Deny access by default and enforce authorization on the server and database.
- NFR-SEC-002: Tenant isolation must be tested with positive and negative cases.
- NFR-SEC-003: Secrets must be kept out of source control and client bundles.
- NFR-SEC-004: Use TLS, managed encryption at rest, secure cookies, rate limits and dependency scanning.
- NFR-REL-001: Database migrations must be version-controlled and reviewed.
- NFR-REL-002: Backups must be tested by restoration, not merely configured.
- NFR-PERF-001: Establish performance targets after estimating expected users, roster sizes and file sizes.
- NFR-ACC-001: Target WCAG 2.2 AA where practicable and test keyboard, contrast, labels and screen-reader basics.
- NFR-OBS-001: Capture structured errors, health signals and security events without leaking sensitive data.
- NFR-MAINT-001: Use typed interfaces, validation schemas, modular code and automated tests.
- NFR-PORT-001: Support current agreed desktop and mobile browsers.

## 5. Acceptance principles
A requirement is not complete until its acceptance criteria pass, its authorization tests pass, errors/loading/empty states are implemented, and documentation is updated.
